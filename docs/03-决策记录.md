# 决策记录（ADR）

> 每条：背景 → 决定 → 理由 → 代价。新决策追加在末尾，不删旧的（推翻时写"被 ADR-xxx 取代"）。

## ADR-001 执行层用无障碍服务，不做自定义启动器
- 背景：产品负责人的需求是一次性大扫除，不想换桌面。
- 决定：用 `AccessibilityService` 操作现有桌面。
- 理由：自定义启动器要用户换掉原桌面，跟"一次性"的定位不符；无障碍是唯一能操作别人桌面、又不需要 root 的正规能力。
- 代价：受限于桌面暴露的节点信息；Google Play 不接受这类用途（我们开源分发，不受影响）。

## ADR-002 优先语义动作，手势拖动兜底
- 背景：Launcher3 为读屏用户提供了"移动项目/创建文件夹"的无障碍动作。
- 决定：首选语义驱动；找不到对应动作时退回手势驱动。
- 理由：语义动作不依赖时序和坐标，速度快、出错少；手势驱动能覆盖更多桌面。
- 代价：两套驱动的维护成本。**前提尚未在真机上验证**（阶段 0 的任务）。

## ADR-003 零第三方依赖
- 决定：不引入 AndroidX、Compose 和任何库。
- 理由：本机 Gradle 缓存可以离线构建，降低假失败/网络超时；无障碍服务和简单界面用框架 API 就够了；开源后别人也更容易构建。
- 代价：界面写法比 Compose 啰嗦。界面变复杂时再评估。

## ADR-004 归类不用大模型（🔒 产品负责人决定）
- 决定：包名词典 → 关键词 → 系统 category 字段 → "其他"，三级规则。
- 理由：离线、零成本、隐私友好（应用列表不出手机）；预览页可以手动纠正。
- 代价：冷门 App 会落到"其他"，词典质量决定体验。

## ADR-005 整理期间不做可玩的小游戏
- 背景：产品负责人提议整理时可以玩小游戏。
- 决定：不做可交互的游戏，改为不可触摸的进度提示条。
- 理由：执行时桌面必须在前台。可触摸的悬浮层会拦截我们注入的手势和用户误触；不可触摸则无法游玩。另外，在悬浮层上触摸，可能被系统当成对桌面的触摸，打断整理。
- 代价：等待期间没有娱乐。用语义驱动缩短总时长来弥补。

## ADR-006 开源协议 MIT
- 理由：最宽松、条文短，产品负责人容易理解；适合个人工具类项目。

## ADR-008 首个适配目标改为 ColorOS 桌面（取代 PRD 中"原生 Launcher3"的假设）
- 背景：2026-10-24 连上产品负责人真机，发现是一加 13、Android 16（SDK 36），默认桌面 `com.android.launcher` 16.4.28，即 ColorOS 桌面，并非 Pixel/AOSP。
- 决定：第一版以产品负责人的 ColorOS 桌面为首个适配目标；AOSP/Pixel 降为第二目标。
- 理由：第一用户就是产品负责人。ColorOS 桌面由 Launcher3 深度改造而来，可能保留了部分无障碍语义动作，但不能假设。
- 代价：ADR-002 的语义驱动可用性变得更不确定，手势驱动的权重上升；具体结论以阶段 0 探针结果为准。

## ADR-009 主色钴蓝，白底 + 分类色（🔒 产品负责人决定）
- 背景：原型 v1 用暖纸底 + 苔绿，产品负责人觉得太常见，要白底为主、多搭点颜色；v1.1 给了珊瑚 / 钴蓝 / 青碧三套主色，他选了钴蓝。
- 决定：色值如下（oklch 为设计源，十六进制由浏览器换算，安卓原生实现直接用十六进制）：

| 用途 | oklch | 十六进制 |
|---|---|---|
| 主色（按钮、强调） | oklch(0.63 0.15 252) | `#3A8CE0` |
| 主色·深（按压态、深色文字） | oklch(0.5 0.15 252) | `#0064B5` |
| 主色·浅底（标签、图标底） | oklch(0.955 0.03 252) | `#E2F2FF` |
| 主色·亮（进度条、描边） | oklch(0.86 0.09 252) | `#A6D5FF` |
| 页面底 | — | `#FFFFFF` |

- 分类色：每类一个色相，浅底 oklch(0.968 0.024·k h) + 深字 oklch(0.48 0.12·k h)，色相见原型 `CATS`。
- 理由：白底贴合主流手机 App；颜色主要花在分类上，它承载"这是哪一类"的信息，不只是装饰。
- 代价：「学习办公」的分类色（色相 250）和主色同为蓝色系，后续如有混淆再调整。

## ADR-010 界面与分类器先行，执行引擎等探针结论（产品负责人决定先开发）
- 背景：产品负责人暂时没空做真机探针测试，要求先按原型开发。
- 决定：先做和执行方式无关的部分：界面全流程、分类器、应用列表读取。「开始整理」按钮先接到一个诚实的提示（"整理引擎还在等真机验证"）；整理中悬浮条和完成页先做成组件。
- 理由：执行驱动（语义还是手势）只影响 Executor，界面和分类器都不依赖它，先做不会白做。
- 代价：扫描页暂用 PackageManager 列出的"已安装应用"代替"桌面上的图标"，两者不完全一致，探针通过后要替换数据源。

## ADR-011 允许测试专用依赖
- 决定：ADR-003 的"零第三方依赖"只约束随 APK 发布的代码；`testImplementation` 可用 JUnit 4 和 org.json（本地 JVM 单测里安卓自带的 org.json 是空实现）。
- 理由：分类器是纯逻辑，值得单测；测试依赖不进 APK。

## ADR-012 字体用系统衬线，不打包 Noto Serif SC
- 决定：标题用 `Typeface.create(Typeface.SERIF, 600, false)`（API 28+；更低版本退回 `Typeface.SERIF`）。
- 理由：中文衬线字体包有十几 MB，打包会让 APK 体积暴涨。原生安卓的系统衬线字体就是 Noto Serif CJK；ColorOS 上效果需要真机确认。

## ADR-013 主驱动定为手势拖动（取代 ADR-002 的"语义优先"）
- 背景：2026-10-24 在产品负责人的一加 13 / ColorOS 16 上实测：
  - 读取桌面：可行。窗口 title=系统桌面，10 页共 54 个应用 + 18 个文件夹全部可读（其他页图标 isVisibleToUser=false，但仍在树里）。
  - 语义驱动：「移动项目」能把图标拎起，但拎起后工作区节点变为 null，没有任何落点动作 → 不可用。
  - 手势驱动（adb motionevent 实测）：按住 1s → 分段移到目标**图案中心** → 悬停 0.9s → 松手，**合成新文件夹 ✅**、**加入已有文件夹 ✅**。松手点在图案边缘会被当成换位。
- 决定：执行引擎以手势驱动为主；瞄准点 = 节点范围水平中心、纵向 top + 48% 高（节点含应用名）。
- 代价：依赖时序和坐标；每步约 3 秒；执行中用户触屏会打断，须保留音量键中止 + 每步读树校验。
- 附带发现：产品负责人手机上同时开着谷歌「开关控制」，它会弹设置向导抢前台、干扰节点读取。整理前应检测其他无障碍服务并提示。

## ADR-014 扫描改为读取真实桌面
- 背景：产品负责人指出"能不能整理"不该等到最后一步才告诉用户；PackageManager 列出 163 个应用，而桌面上只有 54 个，预览页「其他」堆积严重。
- 决定：扫描页直接用无障碍读取桌面（即探针 ① 的能力），读不到就在扫描这一步说明原因。PackageManager 只用来补包名和图标（桌面节点只有应用名）。
- 代价：已在文件夹里的应用要不要参与整理需要新的产品规则（第一版：已有文件夹不拆，见 PRD）。

## ADR-007 不提供撤销，改为整理前提醒截图
- 理由：要撤销，就得把每个图标拖回原来的格子。桌面会自动重排，原位置可能已被占用，没法可靠还原。做一个不可靠的撤销，比没有撤销更伤信任。
